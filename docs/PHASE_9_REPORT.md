# Phase 9 — Production security and staging

Phase 9 extends the existing collector, n8n workflows and dashboard. The staging definition is loopback-only. The current project and legacy stacks remain on their existing configuration until an operator approves cutover.

## Trust boundaries and API

- Browser → dashboard over HTTPS. One trusted operator signs in with a password. The session cookie contains an HMAC-signed token with an eight-hour lifetime. It is host-only, HttpOnly, Secure on HTTPS and SameSite Strict. API routes verify sessions directly. State-changing requests require the exact canonical origin, and the app grants no cross-origin CORS access. Local HTTP is supported only with an explicit loopback origin. Log out clears the client cookie. Rotate the signing key to invalidate all outstanding tokens. Multiple users and per-user job ownership require a separate identity and authorization design.
- Dashboard → n8n uses the server-only `X-Pipeline-Key`. `POST /api/jobs` keeps a stable retry key per submitted payload, drops rights-approval and resume fields and calls `POST /webhook/pipeline-intake`. n8n validates through the worker, creates or resumes a job and responds `202` with `job_id` before continuing its bounded poll. Use `GET /webhook/pipeline-status?job_id=...` or dashboard status for later results. A dashboard submission never provides commercial rights approval.
- n8n → worker uses the existing `Media Worker API Token` header credential. `MEDIA_WORKER_DASHBOARD_TOKEN` has a separate read and intake-validation scope. Job mutations and delivery planning/ledger writes require the n8n worker credential. Worker endpoints retain their methods and payloads. `GET /jobs/{id}` supplies the dashboard's job record.
- `05-ai-curation-probe` and `06-google-drive-delivery` use a separate admin webhook credential. The standalone Drive workflow checks a literal rights-approval boolean before any folder creation or upload. The pipeline retains its rights, mock-curation and manifest checks. The existing collector URL, DNS, redirect and file checks still apply. Dashboard previews stream only allowlisted raster/video types.
- Login and intake limits are process-wide, 10 and 20 per minute respectively. Worker job creation is limited to 20 per minute and retains its in-flight slot limit. These limits assume one dashboard and one worker process. The dashboard caps JSON intake at 16 KiB, login at 2 KiB, and the worker caps JSON requests at 64 KiB even when streamed. The staging edge also caps request bodies.

## Staging setup

1. Use the standalone `deploy/compose.staging.yml` with a separate ignored environment file and an empty staging-only media directory. Grant the container user access to it. Configure `STAGING_HOST` (e.g. `localhost`), `STAGING_HTTPS_PORT` (default 8443), matching `DASHBOARD_ORIGIN` (e.g. `https://localhost:8443`), `STAGING_MEDIA_DIR`, and pinned `N8N_IMAGE` and `CADDY_IMAGE`. Provision distinct random values for `N8N_ENCRYPTION_KEY`, `MEDIA_WORKER_TOKEN`, `MEDIA_WORKER_DASHBOARD_TOKEN`, `N8N_PIPELINE_TOKEN`, `DASHBOARD_SESSION_SECRET` (at least 32 characters), and `DASHBOARD_PASSWORD`. Keep AI disabled and Drive OAuth unset during staging smoke tests. Never copy the legacy n8n encryption key or media into staging.
2. Check configuration with `docker compose --env-file .env.staging -f deploy/compose.staging.yml config -q`. On the approved staging host, bring up that Compose project. The worker has no published port. The dashboard uses Caddy HTTPS on loopback; trust the Caddy internal CA on approved test clients. n8n's setup/editor is on loopback port 5680 by default. On a remote staging host, access these ports via an approved tunnel.
3. In staging n8n, create an owner account, then create Header Auth credentials. Use `Media Worker API Token` with header `X-API-Key` and the worker token, and `Media Pipeline Webhook Token` with header `X-Pipeline-Key` and the pipeline token. Generate the staging pipeline with `node deploy/staging-workflow.mjs` and save its JSON outside version control for import. This export removes access to Drive nodes so n8n can publish without Drive OAuth. Bind the matching credentials on each node, then publish the staging pipeline. Publish `00-health-probe` only if a staging sentinel is available. Keep `05` and `06` unpublished unless their admin credential is separately provisioned. Use the canonical `07` with the Drive integration only after separate approval and credential validation.
4. Check dashboard `/api/ready`, worker `/ready` and n8n `/healthz/readiness`. Check an unauthenticated dashboard request returns 401, then sign in and use a controlled, authorized fixture. Expect an immediate job ID and subsequent status updates. Confirm a direct dashboard-role job mutation returns 403. Readiness checks process and store availability; the authenticated intake smoke test separately verifies workflow publication and credential binding.

## Monitoring and recovery

- Monitor Compose health and bounded Docker logs. Worker request logs contain route templates, HTTP status and duration. Dashboard logs report sign-in and intake results. Alert on persistent readiness failures, submission 429s, and sustained 5xx. The staging n8n defaults suppress saved execution payloads, so collect logs and use authorized fixture runs for diagnosis.
- **Backup.** Record the deployed commit, image tags/digests and workflow IDs. During an approved maintenance window stop writes on the target project, then snapshot the entire media directory including SQLite and any WAL files, and separately snapshot the project n8n state volume. Archive the staging environment and n8n encryption key in encrypted secret storage. Include Caddy state if clients depend on its private CA. Record checksums, restrict access, and retain the pre-change copy.
- **Restore.** Verify checksums, restore into fresh directories and volumes, and provide the matching n8n encryption key. Start the matching application revision in isolation with AI and Drive disabled. Verify database integrity, sample job and manifest reads, file hashes and n8n credential decryption. Verify readiness and a controlled intake before operator-approved cutover.
- **Rollback.** Pause intake, preserve a snapshot of the failed revision and redeploy the previously recorded application images/configuration with their matching workflow exports. Restore the matching snapshots into separate paths only when needed. Recheck readiness, preview authorization and workflow routing before reopening intake. Leave legacy instances and volumes outside all recovery commands.

## Verification and open gates

- Backend: 122 pytest checks passed in isolated Docker with read-only source and workflow binds, no external network and transient job storage. Coverage includes auth scopes, input limits, rate limits, CORS, path confinement, idempotent intake and workflow authentication/rights.
- Frontend: session and routing tests, lint, production build, type check and a production-build HTTP smoke test passed. CI runs the same checks. Four existing lint warnings remain.
- Staging Compose configuration validates with fixture environment values, and the Caddyfile passed `caddy validate` in Caddy 2.10.2. Provisioning a staging host, TLS trust, live n8n credential binding and an operator-approved cutover remain staging acceptance steps. No public deployment, paid AI request or live Drive upload is part of Phase 9.
